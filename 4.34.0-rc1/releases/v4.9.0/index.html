Lean 4.9.0 (2024-07-01)🔗

语言特性、策略与元程序🔗

  • 定义透明性

    • #4053 新增了 seal 与 unseal 命令，使定义在局部范围内变为不可约或半可约。

    • #4061 默认将通过良基递归定义的函数标记为 @[irreducible]， 这应能阻止对此类定义进行代价高昂且往往无益的展开（见下方破坏性变更）。

  • 增量化

    • #3940 将增量精译扩展到声明内部的多个步骤： 定义头部、主体以及策略。

      录屏。

    • 250994 和 67338b 添加了 @[incremental] 属性，用于标记某个精译器支持增量精译。

    • #4259 通过确保仅以受支持的方式进入增量命令与策略，提高了稳健性。

    • #4268 为 := by 添加了特殊处理，使策略块中的游离 token 不会妨碍增量化。

    • #4308 为 have 策略加入增量支持。

    • #4340 修复了错误复用信息树的问题。

    • #4364 为一些谨慎型命令宏加入增量支持，例如 set_option in theorem、theorem foo.bar 和 lemma。

    • #4395 为空白字符处理加入了保守修复，以避免增量复用导致显示文本光标前方的目标。

    • #4407 修复了宏中的非增量命令会阻塞后续增量报告的问题。

    • #4436 修复了项中嵌套策略时的增量报告。

    • #4459 为 next 与 if 策略加入增量支持。

    • #4554 禁用了“策略中的项里的策略”的增量化。

  • 函数归纳

    • #4135 确保函数归纳所使用的名字会被保留。

    • #4327 新增了对反身类型上结构递归的支持。 例如，

      inductive Many (α : Type u) where
  | none : Many α
  | more : α → (Unit → Many α) → Many α

def Many.map {α β : Type u} (f : α → β) : Many α → Many β
  | .none => .none
  | .more x xs => .more (f x) (fun _ => (xs ()).map f)

#check Many.map.induct
/-
Many.map.induct {α β : Type u} (f : α → β) (motive : Many α → Prop)
  (case1 : motive Many.none)
  (case2 : ∀ (x : α) (xs : Unit → Many α), motive (xs ()) → motive (Many.more x xs)) :
  ∀ (a : Many α), motive a
-/

  • #3903 让 Lean 前端在处理前将所有行尾规范化为 LF。 这让 Lean 不再区分 CRLF 与 LF 行尾，提升了跨平台体验，也让 Lake 的哈希真正对应 Lean 实际处理的内容。

  • #4130 让策略框架能够从运行时错误中恢复（例如确定性超时或最大递归深度错误）。

  • split 策略

    • #4211 修复了当 h 有前向依赖时的 split at h。

    • #4349 让用于 if 表达式的 split 可以作用于非命题目标。

  • apply 策略

    • #3929 让 apply 的错误消息在需要时显示合一错误中的隐式参数。 这修改了 MessageData 类型（见下方破坏性变更）。

  • cases 策略

    • #4224 为 cases 策略加入了对 x + 20000 = 20001 这类偏移量合一的支持。

  • omega 策略

    • #4073 让 omega 在构造矛盾证明时可回退为使用经典 Decidable 实例。

    • #4141 和 #4184 修复了错误。

    • #4264 在局部上下文中找不到事实时，改进了 omega 的错误消息。

    • #4358 通过使用 match_expr 改进了 omega 中的表达式匹配。

  • simp 策略

    • #4176 让被擦除引理的名字可以点击。

    • #4208 为判别树键添加了漂亮打印器。

    • #4202 新增 Simp.Config.index 配置选项， 用于控制在选择候选 simp 引理时是否使用完整的判别树。 当 index := false 时，只考虑头函数，与 Lean 3 相同。 这一特性可以帮助用户诊断棘手的 simp 失败，或诊断那些先用 Lean 3 开发、后移植到 Lean 4 的库代码中的问题。

      在下面的示例中，它会报告 foo 是一个有问题的定理。

      opaque f : Nat → Nat → Nat

@[simp] theorem foo : f x (x, y).2 = y := by sorry

example : f a b ≤ b := by
  set_option diagnostics true in
  simp (config := { index := false })
/-
[simp] theorems with bad keys
  foo, key: f _ (@Prod.mk ℕ ℕ _ _).2
-/

      有了上述信息，用户就可以对 foo 这样的定理，在有问题的子项上使用 no_index 进行标注。示例：

      opaque f : Nat → Nat → Nat

@[simp] theorem foo : f x (no_index (x, y).2) = y := by sorry

example : f a b ≤ b := by
  simp -- `foo` is still applied with `index := true`

    • #4274 防止内部 match 方程定理出现在 simp 跟踪中。

    • #4177 和 #4359 让 simp 在策略状态处于恢复模式时，即便某条 simp 引理无法精译，也能继续执行。

    • #4341 修复了对格式错误的定理语法施加 @[simp] 时的 panic。

    • #4345 修复了 simp 错误使用用户指定反向定理的正向版本的问题。

    • #4352 为生成的 congruence 定理的固定参数补上了缺失的 dsimp 化简。

    • #4362 改进了 simp 的跟踪消息，使其中的常量可以悬停。

  • 精译

    • #4046 让 subst 记法（he ▸ h）即便在没有期望类型时，也会尝试双向重写。

    • #3328 为 autoparam 中的标识符提供支持（例如 (h : x = y := by exact rfl) 中的 rfl）。

    • #4096 修改了 let 和 have 中类型的精译方式，要求类型中的任何策略都必须先求值后再继续，从而提升性能。

    • #4215 确保表达式树精译器会对整个算术表达式采用计算出的 “max type”。

    • #4267 让 cases 签名的精译错误即便在主体存在解析错误时也会显示出来。

    • #4368 改进了数值字面量无法合成 OfNat 实例时的错误消息， 包括当该数值的期望类型可能是命题时给出专门的警告消息。

    • #4643 修复了一个会导致嵌套错误消息和信息树消失的问题，其原因是在复用时没有恢复快照子树。

    • #4657 按快照计算错误抑制，因此即便后面还有解析错误，精译错误也能显示出来（RFC #3556）。

  • 元编程

    • #4167 新增 Lean.MVarId.revertAll，用于回退所有自由变量。

    • #4169 新增 Lean.MVarId.ensureNoMVar，用于确保目标的 target 中不含表达式元变量。

    • #4180 为 forallTelescope 方法新增 cleanupAnnotations 参数。

    • #4307 为语法引用中的解析器别名提供支持。

  • 为实现 grind 策略所做的工作

    • 0a515e 和 #4164 添加了 grind_norm 与 grind_norm_proc 属性，以及 @[grind_norm] 定理。

    • #4170, #4221, 和 #4249 创建了 grind 预处理器与核心模块。

    • #4235 和 d6709e 为 grind 添加了专用 cases 策略，并新增 @[grind_cases] 属性，用于标记哪些类型应自动应用该 cases 策略。

    • #4243 为 grind 添加了专用 injection? 策略。

  • 其他修复或改进

    • #4065 修复了 Nat.reduceLeDiff simproc 中的一个错误。

    • #3969 让弃用警告即便在广义字段记法（“点记法”）中也会生效。

    • #4132 修复了 sorry 项会激活隐式 lambda 特性的问题

    • 9803c5 和 47c8e3 将 cdot 与 calc 解析器移动到 Lean 命名空间。

    • #4252 修复了 case 策略，使其通过擦除 tag 上的宏作用域而可在宏中使用。

    • 26b671 和 cc33c3 提取出了 haveId 语法。

    • #4335 修复了部分 calc 策略在存在 mdata 或元变量时的错误。

Lake🔗

  • #4088 改进了 family_def 与 library_data 命令的悬停信息。

  • #4147 为包模板添加默认 README.md

  • #4261 扩展了 lake test 帮助页，添加了 lake check-test 帮助页， 增加了 lake lint 与标签 @[lint_driver]，支持从依赖中指定测试和 lint 驱动， 增加了 testDriverArgs 与 lintDriverArgs 选项，增加了对库测试驱动的支持， 并让 lake check-test 与 lake check-lint 只加载包本身而不加载依赖。

  • #4270 新增 lake pack 与 lake unpack，用于将 Lake 构建产物打包到归档中或从归档中解包。

  • #4083 将 manifest 格式切换为使用 major.minor.patch 语义化版本。 主版本号递增表示破坏性变更（例如新增必填字段，或已有字段语义发生改变）。 次版本号递增（在 0.x 之后）表示向后兼容的扩展（例如新增可选字段、移除字段）。 此变更向后兼容。Lake 仍能成功读取旧的数字版本 manifest， 并会将数字版本 N 视为语义版本 0.N.0。Lake 还会接受带 - 后缀的 manifest 版本 （例如 x.y.z-foo），并忽略该后缀。

  • #4273 出于向后兼容原因，添加了从 JobM 到 FetchM 的提升。

  • #4351 修复了 LogIO 到 CliM 提升的性能问题。

  • #4343 让 Lake 在缓存的构建日志中存储一次构建的依赖 trace，并在重放日志前验证其是否与当前构建的 trace 一致。

  • #4402 将缓存日志移入 trace 文件（不再有 .log.json）。 这意味着致命错误时日志不再被缓存，并确保不会把过期日志关联到最新 trace 上。 此外，.hash 文件的生成也变得更可靠了。 .hash 文件会作为构建过程的一部分被删除，并在使用 --rehash 时总是重新生成。

破坏性变更🔗

尽管大多数改动都可能被视为破坏性变更，本节特别指出了 API 变更。

  • Nat.zero_or 与 Nat.or_zero 已互换（#4094）。

  • IsLawfulSingleton 现为 LawfulSingleton（#4350）。

  • BitVec 字面量记法现在是 <num>#<term> 而不是 <term>#<term>，并且它是全局而非作用域化的。当 x 不是数值字面量时，应使用 BitVec.ofNat w x，而不是 x#w（0d3051）。

  • BitVec.rotateLeft 与 BitVec.rotateRight 现在会对移位量按位宽取模（#4229）。

  • 以下不再是 simp 引理： List.length_pos（#4172）、 Option.bind_eq_some（#4314）。

  • 由于对何种精译问题可以推迟施加了新的限制，let 和 have 中的类型（包括表达式形式与策略形式）现在可能精译失败（#4096）。 特别地，嵌入在类型中的策略将不再利用 let x : type := value; body 这类表达式里 value 的类型。

  • 通过良基递归定义的函数现在默认会被标记为 @[irreducible]（#4061）。 现有那些依赖定义相等成立的证明（例如 rfl）可以 改写为显式展开函数定义（使用 simp、 unfold、rw），或者暂时将递归函数设为 半可约（在命令前使用 unseal f in），或者将函数 定义本身标记为 @[semireducible] 以恢复先前 的行为。

  • 由于 #3929：

    • MessageData.ofPPFormat 构造子已被移除。 它的功能被拆分成两部分：

      • 若要构造惰性的结构化消息，请使用 MessageData.lazy；

      • 若要嵌入 Format 或 FormatWithInfos，请使用 MessageData.ofFormatWithInfos。

      一个迁移示例可见 #3929。

    • MessageData.ofFormat 构造子已改为函数。 如果需要检查 MessageData，可以对 MessageData.ofFormatWithInfos 进行模式匹配。
