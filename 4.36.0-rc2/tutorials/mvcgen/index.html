import Std.Tactic.Doopen Std.Do

前置条件与后置条件🔗

一种编写程序规约的方式是提供前置条件 P，要求程序 \mathit{prog} 的调用方确保它成立，并提供后置条件 Q，要求 \mathit{prog} 确保它成立。 如果在前置条件 P 成立时运行程序 \mathit{prog}，总能使后置条件 Q 成立，就称程序满足该规约。

通常有许多不同的前置条件足以让程序确保后置条件成立。 毕竟，将前置条件 P_1 替换为 P_1 \wedge P_2 就能生成新的前置条件。 程序 \mathit{prog} 与后置条件 Q 的最弱前置条件 \textbf{wp}⟦\mathit{prog}⟧(Q)，是能使 \mathit{prog} 确保 Q 成立、且被所有其他这样的前置条件蕴含的前置条件。

证明程序结果性质的一种方法，是找出保证预期结果的最弱前置条件，再证明该条件直接为真。 这意味着后置条件无论如何都会成立。

循环与不变式🔗

作为 mvcgen 的第一个示例，函数 mySum 使用局部可变状态和 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环计算数组元素之和：

def mySum (l : Array Nat) : Nat := Id.run do let mut out := 0 for i in l do out := out + i return out

若 mySum 正确，它就等于 Array.sum。 在 mySum 中，Lean.Parser.Term.do : termdo 属于内部实现细节，函数签名并未提及任何单子。 因此，证明首先使用引理 Id.of_wp_run_eq 将目标变为适合 mvcgen 的形式。 该引理说明：对于正常终止的 Id 单子计算（Id 计算从不抛出异常），证明保证预期结果的最弱前置条件为真，即可证明关于运行结果的事实。 随后使用 mvcgen 将最弱前置条件表述替换为一组验证条件。

虽然 mvcgen 基本是自动的，但循环仍需要不变式。 循环不变式是循环体既假设又保证成立的陈述；如果在循环开始时为真，则在循环结束时也为真。

注意，情形标签实际上是完整标签的唯一前缀。 引用情形时应只用此前缀；后缀仅提示用户该验证条件的来源。 例如：

  • vc1.step 表示此验证条件证明循环的归纳步骤。

  • vc2.a.pre 用于证明目标假设蕴含某个规约（这里为 forIn）的前置条件。

  • vc3.a.post.success 用于证明某个规约（这里为 forIn）的后置条件蕴含预期性质。

指定循环不变式后，证明可以缩短为 all_goals mleave; grind（其中 mleave 离开有状态证明模式并清理证明状态）。

theorem mySum_correct_short (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum l:Array Natx:Nath:mySum l = x⊢ x = l.sum l:Array Natx:Nath:mySum l = x⊢ ⊢ₛ wp⟦have out := 0; do let __s ← forIn l out fun i __s => have out := __s; have out := out + i; pure (ForInStep.yield out) have out : Nat := __s pure out⟧ (PostCond.noThrow fun a => { down := a = l.sum }) l:Array Natx:Nath:mySum l = x⊢ Invariant l.toList Nat PostShape.purel:Array Natx:Nath:mySum l = xpref✝:List Natcur✝:Natsuff✝:List Nath✝¹:l.toList = pref✝ ++ cur✝ :: suff✝b✝:Nath✝:(Prod.fst ?inv1 ({ «prefix» := pref✝, suffix := cur✝ :: suff✝, property := ⋯ }, b✝)).down⊢ (Prod.fst ?inv1 ({ «prefix» := pref✝ ++ [cur✝], suffix := suff✝, property := ⋯ }, b✝ + cur✝)).downl:Array Natx:Nath:mySum l = x⊢ (Prod.fst ?inv1 ({ «prefix» := [], suffix := l.toList, property := ⋯ }, 0)).downl:Array Natx:Nath:mySum l = xr✝:Nath✝:(Prod.fst ?inv1 ({ «prefix» := l.toList, suffix := [], property := ⋯ }, r✝)).down⊢ r✝ = l.sum case inv1 l:Array Natx:Nath:mySum l = x⊢ Invariant l.toList Nat PostShape.pure All goals completed! 🐙 all_goals l:Array Natx:Nath:mySum l = xr✝:Nath✝:l.toList.sum = r✝⊢ r✝ = l.sum; All goals completed! 🐙

这种模式十分常见，因此 mvcgen 为其提供专门语法：

theorem mySum_correct_shorter (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum l:Array Natx:Nath:mySum l = x⊢ x = l.sum l:Array Natx:Nath:mySum l = x⊢ ⊢ₛ wp⟦have out := 0; do let __s ← forIn l out fun i __s => have out := __s; have out := out + i; pure (ForInStep.yield out) have out : Nat := __s pure out⟧ (PostCond.noThrow fun a => { down := a = l.sum }) mvcgen invariants · ⇓⟨xs, out⟩ => ⌜xs.prefix.sum = out⌝ with All goals completed! 🐙

mvcgen invariants ...with... 是上面 策略序列 mvcgen; case inv1 => ...; all_goals mleave; grind 的简写。后文都将采用这种形式。

将 mySum_correct_shorter 的证明与传统正确性证明比较很有帮助：

theorem mySum_correct_vanilla (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum -- Turn the array into a list cases l with l:List Nat⊢ mySum { toList := l } = { toList := l }.sum -- Unfold `mySum` and rewrite `forIn` to `foldl` l:List Nat⊢ List.foldl (fun b a => b + a) 0 l = l.sum -- Generalize the inductive hypothesis l:List Nat⊢ ∀ (out : Nat), List.foldl (fun x1 x2 => x1 + x2) out l = out + l.sum -- Grind away induction l with All goals completed! 🐙

此证明与 mySum_correct_shorter 中使用 mvcgen 的证明同样简短。 不过，传统方法依赖程序的若干重要性质：

  • Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环不会提前 Lean.Parser.Term.doBreak : doElem`break` exits the surrounding `for` loop.break 或 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return；否则无法将 forIn 重写为 foldl。

  • 循环体 (· + ·) 足够小，可以在证明中重复写出。

  • 循环体不执行底层单子中的任何效应（即只有 Lean.Parser.Term.do : termdo 记法引入的效应）。 Id 单子没有效应，因此其所有计算都是纯的。 虽然仍能将 forIn 重写为 foldlM，但对单子循环体推理可能让 grind 很为难。

后续各节将通过若干示例介绍 mvcgen 及其支持库，同时展示传统证明在何处变得困难。 困难通常来自：

  • Lean.Parser.Term.do : termdo 块使用 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环、Lean.Parser.Term.doBreak : doElem`break` exits the surrounding `for` loop.break 和提前 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return 等控制流构造。

  • 在非 Id 单子中使用效应，会以必须在循环不变式中反映的方式影响隐式单子上下文（状态、异常）。

mvcgen 能以合理的工作量应对这些挑战。

控制流🔗

再看一个将 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环与提前返回组合的示例。 List.Nodup 是断言给定列表不含重复元素的谓词。 下面的函数 nodup 判定此谓词：

def nodup (l : List Int) : Bool := Id.run do let mut seen : Std.HashSet Int := ∅ for x in l do if x ∈ seen then return false seen := seen.insert x return true

如果此函数对满足 List.Nodup 的每个列表返回 true，对不满足它的每个列表返回 false，则函数正确。 与 mySum 一样，Lean.Parser.Term.do : termdo 记法和 Id 单子是 nodup 的内部实现细节。 因此，证明先使用 Id.of_wp_run_eq 将证明状态变为适于 mvcgen 的形式：

theorem nodup_correct (l : List Int) : nodup l ↔ l.Nodup := l:List Int⊢ nodup l = true ↔ l.Nodup l:List Intr:Boolh:nodup l = r⊢ r = true ↔ l.Nodup l:List Intr:Boolh:nodup l = r⊢ ⊢ₛ wp⟦have seen := ∅; do let __s ← forIn l (none, seen) fun x __s => have seen := __s.snd; if x ∈ seen then pure (ForInStep.done (some false, seen)) else have seen := seen.insert x; pure (ForInStep.yield (none, seen)) have __r : Option Bool := __s.fst match __r with | some r => pure r | none => pure true⟧ (PostCond.noThrow fun a => { down := a = true ↔ l.Nodup }) mvcgen invariants · Invariant.withEarlyReturnNewDo (onReturn := fun ret seen => ⌜ret = false ∧ ¬l.Nodup⌝) (onContinue := fun xs seen => ⌜(∀ x, x ∈ seen ↔ x ∈ xs.prefix) ∧ xs.prefix.Nodup⌝) with All goals completed! 🐙

证明具有与最初 mySum 示例相同的简短结构，因为我们再次将全部证明交给 grind 及其已有的 List.Nodup 自动化。 因此，唯一差别在于循环不变式。 由于循环有提前返回，我们用支持可扩展 do 记法精译器的辅助函数 Invariant.withEarlyReturnNewDo 构造不变式。 此函数允许将不变式分为三部分：

  • 循环通过提前返回值 ret 离开后，onReturn ret seen 成立。 对 nodup，唯一会返回的值是 false，表示 nodup 已确定列表确实存在重复。

  • onContinue xs seen 是常规归纳步骤，证明每次迭代都保持不变式。 迭代状态由游标 xs 表示。 此例断言集合 seen 包含此前循环迭代的所有元素，并断言至今没有重复。

  • 循环抛出异常时，onExcept 必须成立。 Id 不含异常，因此这里省略它以使用默认值。 （后面将讨论异常。）

使用霍尔三元组对有效应程序进行组合式推理🔗

前面的示例对用 Id.run Lean.Parser.Term.do : termdo <prog> 定义的函数进行推理，以使用 <prog> 中的局部可变性和提前返回。 但实际程序常使用 Lean.Parser.Term.do : termdo 记法和单子 M，将状态与失败条件隐藏为隐式“效应”。 此时，函数通常省略 M.run。 它们改为具有单子返回类型 M α，并能与返回该类型的其他函数良好组合。 换言之，单子属于函数的接口，而非仅属于实现。

这里的示例包含有状态函数 mkFresh，返回自动递增的计数器值：

structure Supply where counter : Nat def mkFresh : StateM Supply Nat := do let n ← (·.counter) <$> get modify fun s => { s with counter := s.counter + 1 } pure n def mkFreshN (n : Nat) : StateM Supply (List Nat) := do let mut acc := #[] for _ in [:n] do acc := acc.push (← mkFresh) pure acc.toList

霍尔三元组🔗

霍尔三元组由前置条件、语句和后置条件组成；它断言：若前置条件成立，则运行语句后后置条件成立。 Lean 语法写作 ⦃ P ⦄ prog ⦃ Q ⦄，其中 P 是前置条件，prog : m α 是语句，Q 是后置条件。 P 与 Q 使用由具体单子 m 决定的断言语言。Marginal note具体来说，单子的 WP 实例规定断言如何引用单子状态或其可能抛出的异常。

霍尔三元组形式的规约具有组合性，因为它们允许语句依次执行。 若有 ⦃P⦄ stmt1 ⦃Q⦄ 与 ⦃P'⦄ stmt2 ⦃Q'⦄，且 Q 蕴含 P'，则有 ⦃P⦄ (do stmt1; stmt2) ⦃Q'⦄。 正如普通函数的证明可依赖其调用函数的引理，单子程序的证明也可以使用以霍尔三元组给出规约的引理。

将 mkFreshN_correct 转写为霍尔三元组，就得到 mkFresh 的一种合适规约：

⦃⌜True⌝⦄ mkFreshN n ⦃⇓ r => ⌜r.Nodup⌝⦄

角括号将命题嵌入单子断言语言，因此 ⌜p⌝ 是关于命题 p 的断言。 前置条件 ⌜True⌝ 断言 True 为真；用这个平凡前置条件表示规约对调用时的状态没有要求。 后置条件表示结果是不含重复元素的列表。

单步函数 mkFresh 的规约描述其对单子状态的影响：

∀ (c : Nat), ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃⇓ r state => ⌜r = c ∧ c < state.counter⌝⦄

在状态单子中，前置条件可以运行代码前的状态值为参数。 这里全称量化的 Nat 用于关联初始与最终状态；前置条件将其关联到初始状态。 类似地，后置条件也可以接收最终状态作为参数。 此霍尔三元组表示：

若 c 表示前状态 Supply 的 Supply.counter 字段，则运行 mkFresh 会返回 c，并使后状态的 Supply.counter 大于 c。

注意该规约损失了部分信息：mkFresh 将状态增加任意非负量，仍能满足规约。 这是一件好事，因为规约可以抽象掉不重要的实现细节，使证明稳健且简短。

霍尔三元组基于有状态谓词逻辑，以及将单子程序转换到该逻辑中的最弱前置条件语义 wp⟦prog⟧ 定义。 最弱前置条件语义将程序解释为从后置条件到程序保证它所需的最弱前置条件的映射；在此解释下，程序被理解为谓词变换器。 霍尔三元组语法是 Std.Do.Triple 的记法：

-- This is the definition of Std.Do.Triple: def Triple [WP m ps] {α : Type u} (prog : m α) (P : Assertion ps) (Q : PostCond α ps) : Prop := P ⊢ₛ wp⟦prog⟧ Q

WP 类型类将单子 m 映射为 PostShape ps；该 PostShape 决定 Std.Do.Triple 的确切形状。 StateT、ReaderT、ExceptT 等许多标准单子变换器都有典范的 WP 实例。 例如，StateT σ 的 WP 实例给每个 Assertion 添加一个 σ 参数。 有状态蕴涵 ⊢ₛ 会沿这些额外的 σ 参数进行 η-展开。 对于 StateM 程序，以下类型与 Std.Do.Triple 定义等价：

def StateMTriple {α σ : Type u} (prog : StateM σ α) (P : σ → ULift Prop) (Q : (α → σ → ULift Prop) × PUnit) : Prop := ∀ s, (P s).down → let (a, s') := prog.run s; (Q.1 a s').down

常用的后置条件记法 ⇓ r => ... 将类型为 α → Assertion ps 的断言注入到 PostCond α ps 中（⇓ 应像 fun 那样理解）；对于 StateM，通过与空元组 PUnit.unit 配对实现。 引入异常后，后置条件的形状会更加丰富。 记法 ⌜p⌝ 将纯假设 p 嵌入有状态断言。 反过来，若有状态假设 P 与某个 p 的 ⌜p⌝ 等价， 则称它为纯假设。 纯的有状态假设可以自由移入普通 Lean 上下文，再移回来。 （可以用 mpure 策略手动进行。）

组合规约🔗

像 mvcgen [mkFreshN, mkFresh] 这样嵌套展开定义，虽然直接，却对小程序有效。 更具组合性的方式是为每个单子函数建立独立的规约引理。 规约引理是一个霍尔三元组，在验证条件生成期间自动使用，以获得 Lean.Parser.Term.do : termdo 块各语句的前置条件和后置条件。 系统无法自动证明某条语句的后置条件蕴含下一条语句的前置条件时，这一缺失推理步骤就成为验证条件。

规约引理可以作为实参传给 mvcgen，也可以通过 @[spec] 属性注册到全局（或 scoped、local）规约数据库：

@[spec] theorem mkFresh_spec (c : Nat) : ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃⇓ r state => ⌜r = c ∧ c < state.counter⌝⦄ := c:Nat⊢ ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃PostCond.noThrow fun r state => ⌜r = c ∧ c < state.counter⌝⦄ -- Unfold `mkFresh` and blast away: mvcgen [mkFresh] with All goals completed! 🐙 @[spec] theorem mkFreshN_spec (n : Nat) : ⦃⌜True⌝⦄ mkFreshN n ⦃⇓ r => ⌜r.Nodup⌝⦄ := n:Nat⊢ ⦃⌜True⌝⦄ mkFreshN n ⦃PostCond.noThrow fun r => ⌜r.Nodup⌝⦄ -- `mvcgen [mkFreshN, mkFresh_spec]` if `mkFresh_spec` were not -- registered with `@[spec]` mvcgen [mkFreshN] invariants -- As before: · ⇓⟨xs, acc⟩ state => ⌜(∀ x ∈ acc, x < state.counter) ∧ acc.toList.Nodup⌝ with All goals completed! 🐙

关于纯前置条件与框架规则的进阶说明🔗

本小节略有旁逸，初次阅读可以跳过。

假设受 Aeneas 启发的某个单子加法函数 x +? y : M UInt8 的规约 要求加法不溢出，即 h : x.toNat + y.toNat ≤ UInt8.size。 应将此要求编码为规约的普通 Lean 假设（add_spec_hyp），还是用 ⌜·⌝ 记法编码为霍尔三元组的纯前置条件（add_spec_pre）？

theorem add_spec_hyp (x y : UInt8) (h : x.toNat + y.toNat ≤ UInt8.size) : ⦃⌜True⌝⦄ x +? y ⦃⇓ r => ⌜r.toNat = x.toNat + y.toNat⌝⦄ := … theorem add_spec_pre (x y : UInt8) : ⦃⌜x.toNat + y.toNat ≤ UInt8.size⌝⦄ x +? y ⦃⇓ r => ⌜r.toNat = x.toNat + y.toNat⌝⦄ := …

推荐第一种方式，虽然实际中通常没有区别。 验证条件生成器会将纯假设从有状态上下文移入普通 Lean 上下文，因此第二种形式实际上会变成第一种。 这称为将假设框架化（参见 mpure 和 mframe 策略）。 Lean 上下文中的假设属于有状态逻辑不可变的框架，因为与有状态假设不同，它们经过后果规则后仍然保留。

单子变换器与提升🔗

实际程序常使用由多个单子变换器构成的单子，运算也经常从一个单子提升到另一个单子。 验证这些程序时必须考虑这一点。 稍作修改前一个示例即可展示这一情况。

现在，应用包含两个分别由变换器构建的单子：

abbrev CounterM := StateT Supply (ReaderM String) abbrev AppM := StateT Bool CounterM

mkFresh 不再使用 StateM Supply，而使用 CounterM：

def mkFresh : CounterM Nat := do let n ← (·.counter) <$> get modify fun s => { s with counter := s.counter + 1 } pure n

mkFreshN 使用 AppM 定义，后者包含多个状态和读取器效应。 mkFreshN 的定义将 mkFresh 提升到 AppM：

def mkFreshN (n : Nat) : AppM (List Nat) := do let mut acc := #[] for _ in [:n] do let n ← mkFresh acc := acc.push n return acc.toList

随后，基于 mvcgen 的证明无需修改即可通过：

WPMonad 类型类断言 wp⟦prog⟧ 对 Monad 运算保持分配关系（即“单子态射”）。 此证明看起来可能并不比只涉及一个单子时更精彩。 不过，在用户看不到的地方，证明依赖一连串 MonadLift 实例的规约。

异常🔗

若 let mut 是 Lean.Parser.Term.do : termdo 中对应 StateT 的构造，那么提前 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return 就对应 ExceptT。 前面已看到 mvcgen 如何处理 StateT；现在看程序逻辑如何支持 ExceptT。

异常是后置条件类型 PostCond α ps 不仅是成功情形下的单个 α → Assertion ps 条件的原因。 为理解原因，假设它仅包含该条件，且程序 prog 在满足 P 的前状态中抛出异常。 此时应能证明 ⦃P⦄ prog ⦃⇓ r => Q' r⦄ 吗？ （回想一下，⇓ 在语法上类似 fun。） 没有结果 r，因此这个证明对 Q' 意味着什么并不清楚！

受传统程序逻辑中不终止情况的启发，有两种合理的选择：

全正确性解释

⦃P⦄ prog ⦃⇓ r => Q' r⦄ 断言：若 P 成立，则 prog 终止，且结果满足 Q'。

部分正确性解释

⦃P⦄ prog ⦃⇓ r => Q' r⦄ 断言：若 P 成立，且 prog 终止，则结果满足 Q'。

记法 ⇓ r => Q' r 具有全正确性解释，而 ⇓? r => Q' r 具有部分正确性解释。

在上述例子中，⦃P⦄ prog ⦃⇓ r => Q' r⦄ 无法证明，但 ⦃P⦄ prog ⦃⇓? r => Q' r⦄ 可以平凡证明。 不过，这种二选一的情形提示我们，实际存在一系列可表达的正确性性质。 Std.Do 的后置条件概念 PostCond 支持这一系列性质。

例如，假设生成新数字的 Supply 有界，并希望耗尽时抛出异常。 那么 mkFreshN 应仅在供应确实耗尽时抛出异常，如下实现所示：

以下正确性性质表达了这一点：

@[spec] theorem mkFresh_spec (c : Nat) : ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃post⟨fun r state => ⌜r = c ∧ c < state.counter⌝, fun _ state => ⌜c = state.counter ∧ c = state.limit⌝⟩⦄ := c:Nat⊢ ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃(fun r state => ⌜r = c ∧ c < state.counter⌝, fun x state => ⌜c = state.counter ∧ c = state.limit⌝, PUnit.unit)⦄ mvcgen [mkFresh] with All goals completed! 🐙

此性质中的后置条件有两个分支：首个处理正常终止，第二个处理抛出异常。 单子的 WP 实例既决定后置条件有多少分支，也决定每个分支的参数数量：每种可能触发的异常增加一个分支，每层状态增加一个参数。

在新单子中，除类型签名外，mkFreshN 的实现不变：

def mkFreshN (n : Nat) : EStateM String Supply (List Nat) := do let mut acc := #[] for _ in [:n] do acc := acc.push (← mkFresh) pure acc.toList

但规约引理必须在后置条件和循环不变式中同时考虑正常终止及抛出异常：

@[spec] theorem mkFreshN_spec (n : Nat) : ⦃⌜True⌝⦄ mkFreshN n ⦃post⟨fun r => ⌜r.Nodup⌝, fun _msg state => ⌜state.counter = state.limit⌝⟩⦄ := n:Nat⊢ ⦃⌜True⌝⦄ mkFreshN n ⦃(fun r => ⌜r.Nodup⌝, fun _msg state => ⌜state.counter = state.limit⌝, PUnit.unit)⦄ mvcgen [mkFreshN] invariants · post⟨fun ⟨xs, acc⟩ state => ⌜(∀ n ∈ acc, n < state.counter) ∧ acc.toList.Nodup⌝, fun _msg state => ⌜state.counter = state.limit⌝⟩ with All goals completed! 🐙

正如 StateT σ 一类单子变换器使 WP 映射到的 ps 中增加一层 PostShape.arg σ，每个 ExceptT ε 一类的层也增加一层 PostShape.except ε。

每个 PostShape.arg σ 在 Assertion 语言中增加一层 σ → ...。 每个 PostShape.except ε 保持 Assertion 语言不变，但在后置条件中 增加一个异常条件。 因此，EStateM ε σ 的 WP 实例映射到 PostShape PostShape.except ε (.arg σ .pure)， 与 ExceptT ε (StateM σ) 相同。

扩展 mvcgen 以支持自定义单子🔗

mvcgen 框架被设计为可扩展。 此前介绍的单子都没有以任何方式硬编码进 mvcgen。 相反，mvcgen 依赖 WP、WPMonad 类型类实例及用户提供的规约，生成验证条件。

WP 实例定义单子 m 到谓词变换器 PredTrans ps 的最弱前置条件解释， 对应的 WPMonad 实例则断言此转换对 Monad 运算保持分配关系。

假设希望用 mvcgen 为 Aeneas 生成的程序生成验证条件。 Aeneas 将 Rust 程序转换为以下 Result 单子中的 Lean 程序：

inductive Error where | integerOverflow: Error -- ... more error kinds ... inductive Result (α : Type u) where | ok (v: α): Result α | fail (e: Error): Result α | div

Monad Result 和 LawfulMonad Result 实例都已提供。 使 mvcgen 支持该单子需要：

  1. 为 Result 添加 WP 与 WPMonad 实例。

  2. 为加法等基本 Rust 原语的转换结果注册规约引理。

Result 的 WP 实例指定后置条件形状为 .except Error .pure，因为没有类似状态的效应，但存在唯一一种 Error 类型的异常。 WP 实例将 Result α 中的程序转换为 PredTrans ps α 中的谓词变换器。 也就是 PostCond α ps → Assertion ps 类型的函数，将后置条件映射到最弱前置条件。 WP.wp 的实现类似于 Except Error 的实现。 Result 的每种情形都由现有谓词变换器实现：

  • Result.ok 使用 PredTrans.pure；

  • Result.fail 使用 PredTrans.throw；

  • Result.div 使用 PredTrans.const ⌜False⌝，意味着所有规约都断言程序不会发散。

instance : WP Result (.except Error .pure) where wp | .ok v => PredTrans.pure v | .fail e => PredTrans.throw e | .div => PredTrans.const ⌜False⌝

WP.wp 的实现应对基本单子运算保持分配关系。 分别为 pure 和 bind 证明此性质。 对于 bind，需要展开 wp 与 bind 的定义， 暴露嵌套的 match 结构，grind 就能轻松解决。 当谓词变换器应用于后置条件时，就会触发针对它的 simp 与 grind 理论。 使用 ext 可将 WPMonad.wp_pure 与 WPMonad.wp_bind 的目标变为这种形式。

WP 实例的定义决定能够通过 Result.of_wp_eq 从已证明规约中推导哪些性质。 该引理定义“最弱前置条件”的含义。

作为第二部分的示例，以下定义 Result 中的 UInt32 加法，建模整数溢出：

instance : MonadExcept Error Result where throw e := .fail e tryCatch x h := match x with | .ok v => pure v | .fail e => h e | .div => .div def addOp (x y : UInt32) : Result UInt32 := if x.toNat + y.toNat ≥ UInt32.size then throw .integerOverflow else pure (x + y)

有状态目标的证明模式🔗

mvcgen 的首要目标之一，是将单子程序分解为易于理解的验证条件。 例如，单子为单态且所有循环不变式已实例化时，调用 all_goals mleave 应能简化掉所有 Std.Do.SPred 专用构造，留下人类与 grind 容易理解的目标。 循环不变式实例化后，mvcgen 会自动执行这个 all_goals mleave 步骤。

然而，有时 mleave 无法去除全部 Std.Do.SPred 构造。 这时会留下形如 H ⊢ₛ T 的验证条件。 断言语言 Assertion 按以下方式转换为 Std.Do.SPred：

abbrev PostShape.args : PostShape.{u} → List (Type u) | .pure => [] | .arg σ s => σ :: PostShape.args s | .except _ s => PostShape.args s abbrev Assertion (ps : PostShape.{u}) : Type u := SPred (PostShape.args ps)

留下形如 H ⊢ₛ T 的验证条件的一种常见情况，是底层单子 m 为多态。 此时，证明依赖控制到 Assertion 语言转换的 WP m ps 实例，但与 σs : List (Type u) 的确切对应关系尚不明确。 为了成功解决这种验证条件，mvcgen 提供了受 Iris 并发分离逻辑启发的完整证明模式。 （事实上，该证明模式大部分改编自其 Lean 实现 iris-lean。） 策略参考列出全部证明模式策略。
