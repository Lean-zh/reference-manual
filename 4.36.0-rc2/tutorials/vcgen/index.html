本教程自顶向下介绍 vcgen 最重要的概念。 vcgen 可以证明任何具有最弱前置条件语义的程序的性质，从单子计算到小型命令式语言的语法树都包括在内。 本教程重点讨论用 Lean.Parser.Term.do : termdo 记法编写的单子程序，因为这是 Lean 用户最常需要证明性质的可执行程序形式。 运行这些示例前，记得导入 Std.WP 与 Std.Tactic.Do，并打开命名空间 Std.WP 和 Lean.Order：

import Std.WP import Std.Tactic.Doopen Std.WP Lean.Order

前置条件与后置条件🔗

一种编写程序规约的方式是提供前置条件 P，要求程序 \mathit{prog} 的调用方确保它成立，并提供后置条件 Q，要求 \mathit{prog} 确保它成立。 如果在前置条件 P 成立时运行程序 \mathit{prog}，总能使后置条件 Q 成立，就称程序满足该规约。

通常有许多不同的前置条件足以让程序确保后置条件成立。 毕竟，将前置条件 P_1 替换为 P_1 \wedge P_2 就能生成新的前置条件。 程序 \mathit{prog} 与后置条件 Q 的最弱前置条件 \textbf{wp}⟦\mathit{prog}⟧(Q)，是能使 \mathit{prog} 确保 Q 成立、且被所有其他这样的前置条件蕴含的前置条件。

证明程序结果性质的一种方法，是找出保证预期结果的最弱前置条件，再证明该条件直接为真。 这意味着后置条件无论如何都会成立。

循环与不变式🔗

作为 vcgen 的第一个示例，函数 mySum 使用局部可变状态和 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环计算数组元素之和：

def mySum (l : Array Nat) : Nat := Id.run do let mut out := 0 for i in l do out := out + i return out

若 mySum 正确，它就等于 Array.sum。 陈述 mySum l = l.sum 不提及单子，因为 Lean.Parser.Term.do : termdo 是 mySum 的内部实现细节。 因此，下面的证明首先使用引理 Id.of_run_eq_wp，将目标变为 vcgen 可处理的最弱前置条件形式。 该引理说明：对于正常终止的 Id 单子计算（Id 计算从不抛出异常），若能证明保证预期结果的最弱前置条件为真，就能证明关于运行结果的事实。 随后，证明使用 vcgen 将最弱前置条件表述替换为一组验证条件。

虽然 vcgen 基本是自动的，但循环仍需要不变式。 循环不变式是循环体既假设又保证成立的陈述；如果在循环开始时为真，则在循环结束时也为真。

情形标签 vc1、vc2、……按生成时出现的顺序为验证条件编号。 在本证明中：

  • vc1 证明循环开始时不变式成立。

  • vc2 证明最后一次迭代后的不变式蕴含预期性质。

  • vc3 证明每次循环体迭代都保持不变式。

指定循环不变式后，证明可以缩短为仅使用 all_goals grind。

theorem mySum_correct_short (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum l:Array Natx:Nath:mySum l = x⊢ x = l.sum l:Array Natx:Nath:mySum l = x⊢ wp (have out := 0; do let __s ← forIn l out fun i __s => have out := __s; have out := out + i; pure (ForInStep.yield out) have out : Nat := __s pure out) (fun x => x = l.sum) () l:Array Natx:Nath:mySum l = x⊢ Invariant Nat Nat Propl:Array Natx:Nath:mySum l = x⊢ ?inv1 [] (ForIn.toList l) 0l:Array Natx:Nath:mySum l = xa✝¹:Nata✝:?inv1 (ForIn.toList l) [] a✝¹⊢ a✝¹ = l.suml:Array Natx:Nath:mySum l = xpref✝:List Natcur✝:Natsuff✝:List Nat_h✝:ForIn.toList l = pref✝ ++ cur✝ :: suff✝b✝:Nata✝:?inv1 pref✝ (cur✝ :: suff✝) b✝out:Nat := b✝ + cur✝⊢ ?inv1 (pref✝ ++ [cur✝]) suff✝ out case inv1 l:Array Natx:Nath:mySum l = x⊢ Invariant Nat Nat Prop All goals completed! 🐙 all_goals All goals completed! 🐙

这种模式十分常见，因此 vcgen 为其提供专门语法：

theorem mySum_correct_shorter (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum l:Array Natx:Nath:mySum l = x⊢ x = l.sum l:Array Natx:Nath:mySum l = x⊢ wp (have out := 0; do let __s ← forIn l out fun i __s => have out := __s; have out := out + i; pure (ForInStep.yield out) have out : Nat := __s pure out) (fun x => x = l.sum) () vcgen invariants · fun pref suff out => pref.sum = out with All goals completed! 🐙

vcgen invariants ...with... 形式提供不变式，再对每个剩余验证条件运行给定的 grind 步骤；finish 使用 grind 的完整自动化关闭每个条件。后文都将采用这种形式。

将 mySum_correct_shorter 的证明与传统正确性证明比较很有帮助：

theorem mySum_correct_vanilla (l : Array Nat) : mySum l = l.sum := l:Array Nat⊢ mySum l = l.sum -- Turn the array into a list cases l with l:List Nat⊢ mySum { toList := l } = { toList := l }.sum -- Unfold `mySum` and rewrite `forIn` to `foldl` l:List Nat⊢ List.foldl (fun b a => b + a) 0 l = l.sum -- Generalize the inductive hypothesis l:List Nat⊢ ∀ (out : Nat), List.foldl (fun x1 x2 => x1 + x2) out l = out + l.sum -- Grind away induction l with All goals completed! 🐙

此证明与 mySum_correct_shorter 中使用 vcgen 的证明同样简短。 不过，传统方法依赖程序的若干重要性质：

  • Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环不会提前 Lean.Parser.Term.doBreak : doElem`break` exits the surrounding `for` loop.break 或 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return；否则无法将 forIn 重写为 foldl。

  • 循环体 (· + ·) 足够小，可以在证明中重复写出。

  • 循环体不执行底层单子中的任何效应（即只有 Lean.Parser.Term.do : termdo 记法引入的效应）。 Id 单子没有效应，因此其所有计算都是纯的。 虽然仍能将 forIn 重写为 foldlM，但对单子循环体推理可能让 grind 很为难。

后续各节将通过若干示例介绍 vcgen 及其支持库，同时展示传统证明在何处变得困难。 困难通常来自：

  • Lean.Parser.Term.do : termdo 块使用 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环、Lean.Parser.Term.doBreak : doElem`break` exits the surrounding `for` loop.break 和提前 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return 等控制流构造。

  • 在非 Id 单子中使用效应，会以必须在循环不变式中反映的方式影响隐式单子上下文（状态、异常）。

vcgen 能以合理的工作量应对这些挑战。

控制流🔗

再看一个将 Lean.Parser.Term.doFor : doElem`for x in e do s` iterates over `e` assuming `e`'s type has an instance of the `ForIn` typeclass. `break` and `continue` are supported inside `for` loops. `for x in e, x2 in e2, ... do s` iterates over the given collections in parallel, until at least one of them is exhausted. The types of `e2` etc. must implement the `Std.ToStream` typeclass.for 循环与提前返回组合的示例。 List.Nodup 是断言给定列表不含重复元素的谓词。 下面的函数 nodup 判定此谓词：

def nodup (l : List Int) : Bool := Id.run do let mut seen : Std.HashSet Int := ∅ for x in l do if x ∈ seen then return false seen := seen.insert x return true

如果此函数对满足 List.Nodup 的每个列表返回 true，对不满足它的每个列表返回 false，则函数正确。 与 mySum 一样，Lean.Parser.Term.do : termdo 记法和 Id 单子是 nodup 的内部实现细节。 因此，证明先使用 Id.of_run_eq_wp 将证明状态转换为适于 vcgen 的形式：

-- A future 4.36 release adds these annotations to the library. attribute [local grind norm] Lean.Order.ofProp_prop_eq Lean.Order.meet_prop_eq_and Lean.Order.join_prop_eq_or Lean.Order.iSup_prop_eq_exists theorem nodup_correct (l : List Int) : nodup l ↔ l.Nodup := l:List Int⊢ nodup l = true ↔ l.Nodup l:List Intr:Boolh:nodup l = r⊢ r = true ↔ l.Nodup l:List Intr:Boolh:nodup l = r⊢ wp (have seen := ∅; do let __s ← forIn l (none, seen) fun x __s => have seen := __s.snd; if x ∈ seen then pure (ForInStep.done (some false, seen)) else have seen := seen.insert x; pure (ForInStep.yield (none, seen)) have __r : Option Bool := __s.fst match __r with | some r => pure r | none => pure true) (fun r => r = true ↔ l.Nodup) () vcgen invariants · Invariant.withEarlyReturnNewDo (onReturn := fun ret seen => ret = false ∧ ¬l.Nodup) (onContinue := fun pref suff seen => (∀ x, x ∈ seen ↔ x ∈ pref) ∧ pref.Nodup) with All goals completed! 🐙

证明与 mySum 的证明结构相同：grind 使用已有的 List.Nodup 自动化解决全部验证条件，只有循环不变式不同。 由于循环有提前返回，我们用支持可扩展 do 记法精译器的辅助函数 Invariant.withEarlyReturnNewDo 构造不变式。 此函数允许将不变式分为两部分：

  • 循环通过提前返回值 ret 离开后，onReturn ret seen 成立。 对 nodup，唯一会返回的值是 false，表示 nodup 已确定列表确实存在重复。

  • onContinue pref suff seen 是每次正常迭代后成立的不变式。 与 mySum 一样，列表 pref 保存循环已访问的元素，suff 保存尚未访问的元素。 此例断言集合 seen 包含此前循环迭代的所有元素，并断言至今没有重复。

几点观察：

  • 它比使用 vcgen 的证明还短。

  • 用 generalize 泛化累加器，依赖恰好只有一处 ∅ 可泛化；否则必须将部分程序复制进证明。对于较大函数，这不可接受。

  • 给出适当引理后，grind 可以按函数控制流拆分，并对 Id 推理。 虽然 Id.run_pure 和 Id.run_bind 可以这样使用，但 Id.run_seq 不行，因为该引理不支持E-匹配。 如果 grind 失败，就只能手动完成全部控制流拆分和单子推理，直到它能够再次接手。

避免在证明中重复定义控制流的常见方法是使用 fun_cases 或 fun_induction。 遗憾的是，fun_cases 无助于处理 forIn 应用内部的控制流。 而使用 vcgen 的证明从不需要复制原程序的任何部分。 vcgen 自带对许多 forIn 实现的支持；对自定义 forIn，可以用标注 @[spec] 的规约引理提供支持。 编写此类引理需要相当多工作，因为循环规约以不变式为参数，且必须证明循环保持它。 Std.Internal.PureForIn 实例所需工作较少：它声明容器上的循环就是其元素列表 ForIn.toList 上的循环。 有了此实例，vcgen 自带的循环规约就适用于该容器。

使用霍尔三元组对有效应程序进行组合式推理🔗

前面的示例对用 Id.run Lean.Parser.Term.do : termdo <prog> 定义的函数进行推理，以使用 <prog> 中的局部可变性和提前返回。 但实际程序常使用 Lean.Parser.Term.do : termdo 记法和单子 M，将状态与失败条件隐藏为隐式“效应”。 此时，函数通常省略 M.run。 它们改为具有单子返回类型 M α，并能与返回该类型的其他函数良好组合。 换言之，单子属于函数的接口，而非仅属于实现。

这里的示例包含有状态函数 mkFresh，返回自动递增的计数器值：

structure Supply where counter : Nat def mkFresh : StateM Supply Nat := do let n ← (·.counter) <$> get modify fun s => { s with counter := s.counter + 1 } pure n def mkFreshN (n : Nat) : StateM Supply (List Nat) := do let mut acc := #[] for _ in [:n] do acc := acc.push (← mkFresh) pure acc.toList

mkFreshN n 返回 n 个“新鲜”数字，通过 mkFresh 修改内部 Supply 状态。 “新鲜”表示此前生成的所有数字都与下一个生成的数字不同。 可以用 List.Nodup 表述并证明正确性性质 mkFreshN_correct：返回的数字列表不应包含重复。 此证明中的 StateM.of_run'_eq_wp 承担此前示例中 Id.of_run_eq_wp 的角色。

theorem mkFreshN_correct (n : Nat) : ((mkFreshN n).run' s).Nodup := s:Supplyn:Nat⊢ List.Nodup (StateT.run' (mkFreshN n) s) -- Focus on `(mkFreshN n).run' s`. s:Supplyn:Natx:Id (List Nat)h:StateT.run' (mkFreshN n) s = x⊢ List.Nodup x s:Supplyn:Natx:Id (List Nat)h:StateT.run' (mkFreshN n) s = x⊢ wp (mkFreshN n) (fun a x => a.Nodup) () s -- Show something about monadic program `mkFresh n`. -- The `mkFreshN` and `mkFresh` arguments make `vcgen` unfold -- these definitions. vcgen [mkFreshN, mkFresh] invariants -- Invariant: The counter is larger than any accumulated number, -- and all accumulated numbers are distinct. -- Note that the invariant may refer to the state through function -- argument `state : Supply`. Since the next number to accumulate is -- the counter, it is distinct to all accumulated numbers. · fun pref suff acc state => (∀ x ∈ acc, x < state.counter) ∧ acc.toList.Nodup with All goals completed! 🐙

此证明展开了 mkFreshN 和 mkFresh。 在更大的程序中，许多函数会调用 mkFresh，每个像上述那样的证明都会再次展开它。 我们可以改为只陈述并证明一次 mkFresh 的行为，然后在每次调用时使用它。 只使用函数规约而从不使用其代码的证明，称为模块化证明。 霍尔三元组是有效应程序规约的标准形式，使这种模块化推理成为可能。

霍尔三元组🔗

霍尔三元组由前置条件、语句和后置条件组成；它断言：若前置条件成立，则运行语句后后置条件成立。 Lean 语法写作 ⦃ P ⦄ prog ⦃ Q ⦄，其中 P 是前置条件，prog : m α 是语句，Q 是后置条件。 P 与 Q 使用由具体单子 m 决定的断言语言。Marginal note具体来说，单子的 WP 类型类实例规定断言如何引用单子状态或其可能抛出的异常。 可以在分号后显式提供异常后置条件，例如 ⦃ P ⦄ prog ⦃ Q; E ⦄。 省略异常后置条件时，默认为底元断言 ⊥，断言程序不会抛出异常。 下文“异常”一节展示抛出异常的程序的后置条件。

将 mkFreshN_correct 转写为霍尔三元组，就得到 mkFreshN 的一种合适规约：

⦃fun _ => True⦄ mkFreshN n ⦃fun r _ => r.Nodup⦄

对于 StateM 程序，断言是状态上的谓词，后置条件还以返回值作为首个参数。 前置条件 fun (_ : Supply) => True 对调用程序时的状态不提出任何要求。 后置条件说明结果值是不含重复元素的列表，与最终状态无关。

单步函数 mkFresh 的规约描述其对单子状态的影响：

∀ (c : Nat), ⦃fun state => state.counter = c⦄ mkFresh ⦃fun r state => r = c ∧ c < state.counter⦄

全称量化的 c 是逻辑变量，关联初始状态、结果及最终状态。 此霍尔三元组表示：

若 c 表示前状态 Supply 的 Supply.counter 字段，则运行 mkFresh 会返回 c，并使后状态的 Supply.counter 大于 c。

注意该规约损失了部分信息：mkFresh 将状态增加任意非负量，仍能满足规约。 这是一件好事，因为规约可以抽象掉不重要的实现细节，使证明稳健且简短。

三元组 ⦃ P ⦄ prog ⦃ Q ⦄ 表示 P ⊑ wp prog Q ⊥：前置条件蕴含本教程开头介绍的最弱前置条件。 最弱前置条件语义 wp 将程序解释为将后置条件映射为前置条件的谓词变换器。 霍尔三元组语法是 Std.WP.Triple 的记法，其定义如下，省略了部分绑定：

structure Triple ... (x : Prog) [WP Prog Value Pred EPred]
    (pre : Pred) (post : Value → Pred) (epost : EPred) : Prop where
  intro ::
  le_wp : pre ⊑ wp x post epost

WP 类型类将结果类型为 Value 的程序类型 Prog 解释为断言类型 Pred 和异常断言类型 EPred 上的谓词变换器。 StateT、ReaderT、ExceptT 等许多标准单子和单子变换器都有典范的 WP 实例。 例如，StateT σ 的 WP 实例给每个断言添加一个 σ 参数。 定义中的蕴涵 ⊑ 是断言格的序关系；对 StateM，它是逐点蕴涵。 对 StateM 程序，以下类型等价于 Std.WP.Triple：

def StateMTriple {α σ : Type} (prog : StateM σ α) (P : σ → Prop) (Q : α → σ → Prop) : Prop := ∀ s, P s → let (a, s') := prog.run s; Q a s'

霍尔三元组形式的规约具有组合性，因为它们允许语句依次执行。 由 ⦃P⦄ stmt1 ⦃fun _ => R⦄ 和 ⦃R⦄ stmt2 ⦃Q⦄ 可得 ⦃P⦄ (do stmt1; stmt2) ⦃Q⦄。 正如普通函数的证明可依赖其调用函数的引理，单子程序的证明也可以使用以霍尔三元组给出规约的引理。

组合规约🔗

上一节的规约会成为规约引理。 规约引理是一个霍尔三元组，在验证条件生成期间自动使用，以取得 Lean.Parser.Term.do : termdo 块中各条语句的前置条件和后置条件。 系统无法自动证明某条语句的后置条件蕴含下一条语句的前置条件时，这一缺失推理步骤就成为验证条件。

规约引理可以作为实参传给 vcgen，也可以通过 @[spec] 属性注册到全局（或 scoped、local）规约数据库：

@[spec] theorem mkFresh_spec (c : Nat) : ⦃fun state => state.counter = c⦄ mkFresh ⦃fun r state => r = c ∧ c < state.counter⦄ := c:Nat⊢ ⦃ fun state => state.counter = c ⦄ mkFresh ⦃ fun r state => r = c ∧ c < state.counter ⦄ -- Unfold `mkFresh` and blast away: vcgen [mkFresh] with All goals completed! 🐙 @[spec] theorem mkFreshN_spec (n : Nat) : ⦃fun _ => True⦄ mkFreshN n ⦃fun r _ => r.Nodup⦄ := n:Nat⊢ ⦃ fun x => True ⦄ mkFreshN n ⦃ fun r x => r.Nodup ⦄ -- `vcgen [mkFreshN, mkFresh_spec]` if `mkFresh_spec` were not -- registered with `@[spec]` vcgen [mkFreshN] invariants -- As before: · fun pref suff acc state => (∀ x ∈ acc, x < state.counter) ∧ acc.toList.Nodup with All goals completed! 🐙

单子变换器与提升🔗

实际程序常使用由多个单子变换器构成的单子，运算也经常从一个单子提升到另一个单子。 验证这些程序时必须考虑这一点。 稍作修改前一个示例即可展示这一情况。

现在，应用包含两个分别由变换器构建的单子：

abbrev CounterM := StateT Supply (ReaderM String) abbrev AppM := StateT Bool CounterM

mkFresh 不再使用 StateM Supply，而使用 CounterM：

def mkFresh : CounterM Nat := do let n ← (·.counter) <$> get modify fun s => { s with counter := s.counter + 1 } pure n

mkFreshN 使用 AppM 定义，后者包含多个状态和读取器效应。 mkFreshN 的定义将 mkFresh 提升到 AppM：

def mkFreshN (n : Nat) : AppM (List Nat) := do let mut acc := #[] for _ in [:n] do let n ← mkFresh acc := acc.push n return acc.toList

规约引理只有两处变化：纯命题部分用角括号包裹，不变式为 AppM 的 Bool 状态增加一个实参：

@[spec] theorem mkFresh_spec (c : Nat) : ⦃fun state => ⌜state.counter = c⌝⦄ mkFresh ⦃fun r state => ⌜r = c ∧ c < state.counter⌝⦄ := c:Nat⊢ ⦃ fun state => ⌜state.counter = c⌝ ⦄ mkFresh ⦃ fun r state => ⌜r = c ∧ c < state.counter⌝ ⦄ vcgen [mkFresh] with All goals completed! 🐙 @[spec] theorem mkFreshN_spec (n : Nat) : ⦃⌜True⌝⦄ mkFreshN n ⦃fun r => ⌜r.Nodup⌝⦄ := n:Nat⊢ ⦃ ⌜True⌝ ⦄ mkFreshN n ⦃ fun r => ⌜r.Nodup⌝ ⦄ vcgen [mkFreshN] invariants · fun pref suff acc _ state => ⌜(∀ n ∈ acc, n < state.counter) ∧ acc.toList.Nodup⌝ with All goals completed! 🐙

角括号 ⌜p⌝ 将命题 p 作为纯断言嵌入断言语言，其成立与状态无关。 在 CounterM 中，断言先接收 Supply 状态，再接收读取器的 String 环境。 mkFresh_spec 的前置条件只绑定状态；⌜state.counter = c⌝ 是关于环境的纯断言：若 state.counter = c 成立，则它对每个环境都成立。

这些证明看起来可能并不比只涉及单个单子的证明更精彩。 不过，在用户看不到的地方，证明依赖一连串 MonadLift 实例的规约。 它们也依赖 StateT 和 ReaderT 的 WPMonad 实例，使 pure 与 bind 的规约在每层都可用。 WPMonad 实例只要求 pure 与 bind 的最弱前置条件至少与谓词变换器单子计算出的条件一样弱。 换言之，wp 是有序单子之间的松态射。

异常🔗

若 let mut 是 Lean.Parser.Term.do : termdo 中对应 StateT 的构造，那么提前 Lean.Parser.Term.doReturn : doElem`return e` inside of a `do` block makes the surrounding block evaluate to `pure e`, skipping any further statements. Note that uses of the `do` keyword in other syntax like in `for _ in _ do` do not constitute a surrounding block in this sense; in supported editors, the corresponding `do` keyword of the surrounding block is highlighted when hovering over `return`. `return` not followed by a term starting on the same line is equivalent to `return ()`.return 就对应 ExceptT。 前面已看到 vcgen 如何处理 StateT；现在看看程序逻辑如何支持 ExceptT。

异常是三元组除成功后置条件外还要携带异常后置条件的原因。 为理解原因，假设只有成功后置条件，且程序 prog 在满足 P 的前状态中抛出异常。 此时应当能证明 ⦃P⦄ prog ⦃Q'⦄ 吗？ 由于不存在结果值，这个证明对 Q' 意味着什么并不清楚！

受传统程序逻辑中不终止情况的启发，有两种合理的选择：

全正确性解释

⦃P⦄ prog ⦃Q'⦄ 断言：若 P 成立，则 prog 正常终止，且结果满足 Q'。

部分正确性解释

⦃P⦄ prog ⦃Q'; ⊤⦄ 断言：若 P 成立，且 prog 正常终止，则结果满足 Q'。

不显式提供异常后置条件的三元组使用底元断言 (⊥ : EPred)，因此采用全正确性解释：异常必须使 ⊥ 成立，所以不允许抛出异常。 顶元断言 (⊤ : EPred) 允许所有异常，产生部分正确性解释。

对上述例子，⦃P⦄ prog ⦃Q'⦄ 无法证明，但 ⦃P⦄ prog ⦃Q'; ⊤⦄ 可平凡证明。 在 (⊥ : EPred) 与 (⊤ : EPred) 之间，异常后置条件表达一系列不同的正确性性质。

例如，假设生成新数字的 Supply 有界，并希望耗尽时抛出异常。 那么 mkFresh 应仅在供应确实耗尽时抛出异常，如以下实现：

structure Supply where counter : Nat limit : Nat property : counter ≤ limit def mkFresh : EStateM String Supply Nat := do let supply ← get if h : supply.counter = supply.limit then throw s!"Supply exhausted: {supply.counter} = {supply.limit}" else let n := supply.counter have := supply.property set { supply with counter := n + 1, property := supply:Supplyh:¬supply.counter = supply.limitn:Nat := supply.counterthis:supply.counter ≤ supply.limit⊢ n + 1 ≤ supply.limit All goals completed! 🐙 } pure n

以下正确性性质表达了这一点：

@[spec] theorem mkFresh_spec (c : Nat) : ⦃fun state => state.counter = c⦄ mkFresh ⦃fun r state => r = c ∧ c < state.counter; fun _ state => c = state.counter ∧ c = state.limit⦄ := c:Nat⊢ ⦃ fun state => state.counter = c ⦄ mkFresh ⦃ fun r state => r = c ∧ c < state.counter; fun x state => c = state.counter ∧ c = state.limit ⦄ vcgen [mkFresh] with All goals completed! 🐙

分号后的异常后置条件在 mkFresh 抛出异常时适用。 单子的 WP 实例决定两种后置条件的类型：异常后置条件接收抛出的异常而非结果值，每层状态再提供一个额外参数。

在新单子中，除类型签名外，mkFreshN 的实现不变：

def mkFreshN (n : Nat) : EStateM String Supply (List Nat) := do let mut acc := #[] for _ in [:n] do acc := acc.push (← mkFresh) pure acc.toList

不过，规约引理必须同时考虑正常终止与抛出异常；循环不变式则保持不变：

@[spec] theorem mkFreshN_spec (n : Nat) : ⦃fun _ => True⦄ mkFreshN n ⦃fun r _ => r.Nodup; fun _msg state => state.counter = state.limit⦄ := n:Nat⊢ ⦃ fun x => True ⦄ mkFreshN n ⦃ fun r x => r.Nodup; fun _msg state => state.counter = state.limit ⦄ vcgen [mkFreshN] invariants · fun pref suff acc state => (∀ n ∈ acc, n < state.counter) ∧ acc.toList.Nodup with All goals completed! 🐙

StateT σ 层将断言类型 Pred 变为 σ → Pred，异常后置条件类型不变。 ExceptT ε 层保持断言类型不变，将异常后置条件类型 EPred 变为 (ε → Pred) × EPred，增加一个 ε → Pred 类型的异常分支。 EStateM ε σ 的 WP 实例使用 σ → Prop 类型的断言与 ε → σ → Prop 类型的异常后置条件，对应等价变换器栈 ExceptT ε (StateM σ) 的单个异常分支。

扩展 vcgen 以支持自定义单子🔗

vcgen 框架被设计为可扩展。 此前介绍的单子都没有以任何方式硬编码进 vcgen。 相反，vcgen 依赖 WP、WPMonad 类型类实例和用户提供的规约，生成验证条件。 每个程序类型需要 WP 实例，单子还需要 WPMonad 实例。 本节为一个自定义单子构造这两个实例。

WP 实例定义单子 m 到谓词变换器 PredTrans Pred EPred α 的最弱前置条件解释， 对应的 WPMonad 实例则断言此转换对 pure 与 bind 可靠。

假设希望用 vcgen 为 Aeneas 生成的程序生成验证条件。 Aeneas 将 Rust 程序转换为以下 Result 单子中的 Lean 程序：

inductive Error where | integerOverflow: Error -- ... more error kinds ... inductive Result (α : Type u) where | ok (v: α): Result α | fail (e: Error): Result α | div

Monad Result 和 LawfulMonad Result 实例都已提供。 使 vcgen 支持该单子需要：

  1. 为 Result 添加 WP 与 WPMonad 实例。

  2. 为加法等基本 Rust 原语的转换结果注册规约引理。

Result 的 WP 实例指定断言类型为 Prop，因为没有类似状态的效应；异常后置条件类型为 Error → Prop，因为只有一种类型为 Error 的异常。 WP 实例将 Result α 中的程序转换为 PredTrans Prop (Error → Prop) α 中的谓词变换器。 也就是将后置条件与异常后置条件映射到最弱前置条件的函数。 WP.wp 的实现类似于 Except Error 的实现。 Result 的每种情形直接决定前置条件：

  • Result.ok v 产生在 v 处的成功后置条件。

  • Result.fail e 产生在 e 处的异常后置条件。

  • Result.div 产生 False，意味着所有规约都断言程序不会发散。

解决验证条件🔗

vcgen 的首要目标之一，是将程序分解为易于理解的验证条件。 验证条件是普通 Lean 目标，因此可以使用任何策略解决。 当断言语言具体时（如 Id 或 StateM 程序），目标直接描述结果值和状态，可使用 grind。

生成验证条件时，vcgen 将目标上下文内部化到 grind 的 E-图中。 with 子句在该共享上下文中对每个剩余验证条件运行一个 grind 模式步骤，避免对各个条件重复内部化上下文。 finish 使用 grind 的完整自动化关闭验证条件。
