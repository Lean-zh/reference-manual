26.3. 实现代码检查器🔗

许多大型项目需要自定义检查器来落实项目特定标准。 定义新检查器的步骤是：

  1. 注册控制新检查器的选项。

  2. 确定它应是命令检查器、模块检查器、有状态检查器还是环境检查器。

  3. 决定需要保存哪些代码质量度量（若有）。

  4. 实现所需的包级代码质量检查。

定义检查器首先要注册控制它的选项。 使用 Lean.Option.registerOption : commandregister_option 注册选项，需要提供新选项的默认值和说明。 默认值决定检查器是否默认启用。 在模块中，该选项应公开并位于元阶段。 检查器应由 Bool 选项控制。 用于配置检查器的其他选项（例如阈值）可以添加到检查器自身的命名空间中。

检查器应使用 logLint 或 Lean.Linter.logLintIf 显示检查警告，而不是使用 Lean.logWarning。 这些辅助函数确保检查警告格式统一。 它们还会在内部将消息标记为检查器消息，使 Lake 和 Lean 将其包含在 lake lint 的输出中。 logLintIf 还会正确解析检查器选项值，考虑 linter.all 和检查器集合。 logLint 应用于已经检查过该检查器选项的上下文。

一些检查器在准备记录警告前，就需要检查自己是否启用。 例如，计算开销大且不产生有用代码质量度量的检查器，可能希望在未启用时尽早退出。 这些检查器应使用正确考虑检查器集合及 linter.all 的辅助函数判断是否启用。 具体做法是先调用 Lean.Linter.getLinterOptions，再用 Lean.Linter.getLinterValue 检查选项值。

最后，每个检查器实现都应使用 Lean.withSetOptionIn 包裹针对具体命令的检查。 缺少这个包装时，针对被检查命令设置的 Lean.Parser.Command.set_option : command`set_option <id> <value>` 将选项 `<id>` 设置为 `<value>`。 根据选项类型，值可以为 `true`、`false`、字符串或数字。 选项用于配置 Lean 以及用户自定义扩展的行为。 设置持续有效至当前 `section` 或 `namespace` 结束，或文件结束。 `<id>` 支持自动补全，可列出可用选项。 `set_option <id> <value> in <command>` 仅为单条命令设置选项： ``` set_option pp.all true in #check 1 + 1 ``` 类似地，也可在项和策略内部使用 `set_option <id> <value> in`，使选项仅在单个项或策略中生效。set_option...Lean.Parser.Command.in : commandin ... 将不会被考虑。 命令和有状态检查器应包装整个实现，模块检查器则应包装对单个命令的操作。

是否启用某个代码检查选项，按以下顺序确定：

  1. 如果显式设置了该选项，则由其值决定是否启用。

  4. 否则，由该选项的默认值决定是否启用。

给定一个处理命令语法的函数 cmd，返回一个新函数：先递归剥离并求值 set_option ... in ... 语法，相应地更新选项，再对内层语法调用 cmd。 结果类型任意，因此除了 CommandElab，也能包装返回值的函数，例如有状态检查器的各个阶段。

预期在精译完成后的代码检查器中使用它。 它不适用于外层 set_option 的常规精译，因为它：

  • 不会在信息树中记录 set_option 命令的信息；

  • 会静默忽略设置选项时的失败（例如选项未知或值的类型不正确时不会报错），因为这些问题应当已在原始精译过程中报告。

26.3.1. 命令检查器🔗

命令检查器是最简单的检查器形式。 命令检查器是 Lean.Elab.Command.Linter 类型的值；该结构体有一个类型为 Syntax → CommandElabM Unit 的 run 字段。 addLinter 保存一个新命令检查器，必须在 Lean.Parser.Command.initialize : commandinitialize 块中运行。 在模块中使用时，Lean.Parser.Command.initialize : commandinitialize 块必须位于元阶段。

每条命令精译后都会运行命令检查器，与文件剩余部分的精译并发执行。 检查器的 run 函数应用于命令语法，所在上下文可访问命令的信息树。 检查器对环境所作的修改会被丢弃，但新消息日志条目、代码操作及代码质量度量会被保存。

统计策略数量

此自定义检查器在命令的策略数超过可配置阈值时发出警告。 它处理命令的信息树，记录具有策略信息且种类为策略种类的原始语法的唯一开始位置，以找到策略。 由于宏展开步骤及同一策略的重复执行都会保存策略信息，因此需要去重。 检查器未启用时会尽早退出，而不是到准备记录消息时才作决定。

Steps/Linter.leanmodule public meta import Lean.Linter.Basic public meta import Lean.Elab.InfoTree.Util open Lean Elab Command open Std (HashSet) meta section public register_option linter.tacticCount : Bool := { defValue := true descr := "warn when a command runs many tactics" } public register_option linter.tacticCount.max : Nat := { defValue := 100 descr := "the number of tactics a command may run before \ `linter.tacticCount` warns" } open Parser in /-- Whether `kind` is the syntax kind of a tactic, as opposed to a tactic sequence or block. -/ def isTacticKind (env : Environment) (kind : SyntaxNodeKind) : Bool := match (parserExtension.getState env).categories.find? `tactic with | some category => category.kinds.contains kind | none => false /-- The number of distinct tactics from the source file that were run while elaborating `tree`. -/ def countTactics (env : Environment) (tree : InfoTree) : Nat := let positions : HashSet String.Pos.Raw := tree.foldInfo (init := {}) fun _ info positions => match info with | .ofTacticInfo ti => match ti.stx.getHeadInfo, ti.stx.getPos? with | .original .., some pos => if isTacticKind env ti.stx.getKind then positions.insert pos else positions | _, _ => positions | _ => positions positions.size open Linter in /-- Warns when a command runs more than `linter.tacticCount.max` tactics. -/ def tacticCount : Linter where run := withSetOptionIn fun stx => do -- Don't compute the result if it will never be shown unless getLinterValue linter.tacticCount (← getLinterOptions) do return let env ← getEnv let count := (← getInfoState).trees.foldl (init := 0) fun n t => n + countTactics env t let limit := linter.tacticCount.max.get (← getOptions) if count > limit then Linter.logLint linter.tacticCount stx m!"this command runs \ {count} tactics, more than {limit}" initialize addLinter tacticCount

26.3.2. 模块检查器🔗

模块检查器在每个模块精译完成后运行。 模块检查器的类型为 Lean.Elab.Command.ModuleLinter；该结构体具有类型为 Array Syntax → CommandElabM Unit 的 run 函数。 调用时会将该模块中的所有顶层命令传给此函数。 由于整个模块精译完毕后才调用检查器，警告要到精译末尾才会出现。

与命令检查器不同，模块检查器不能访问命令的信息树，也不能保存代码操作。 不过，它们可以访问模块的最终环境。 因此，它们主要适合语法检查。 若全文件检查需要信息树，应考虑使用有状态检查器。

addModuleLinter 保存一个新模块检查器，必须在 Lean.Parser.Command.initialize : commandinitialize 块中运行。 在模块中使用时，Lean.Parser.Command.initialize : commandinitialize 块必须位于元阶段。

限制声明数量

模块 Limit.Linter 包含一个模块检查器，在模块声明过多时发出警告。 上限由选项值决定。 虽然警告附着于首个超出限制的声明，但由于由模块检查器实现，它要到整个文件精译完成后才会出现。

Limit/Linter.leanmodule public meta import Lean.Linter.Basic open Lean Elab Command meta section public register_option linter.declarationLimit : Bool := { defValue := true descr := "warn when a file contains more declarations than \ `linter.declarationLimit.max`" } public register_option linter.declarationLimit.max : Nat := { defValue := 200 descr := "the number of declarations that a file may contain" } /-- Warns at the first declaration past the limit. -/ def declarationLimit : ModuleLinter where run cmds := do let limit := linter.declarationLimit.max.get (← getOptions) let decls := cmds.filter (·.isOfKind ``Parser.Command.declaration) if h : limit < decls.size then Linter.logLintIf linter.declarationLimit decls[limit] m!"this file contains {decls.size} declarations, more than \ {limit}" initialize addModuleLinter declarationLimit

此模块将最大声明数设为 2：

Limit/Test.leanmodule import Limit.Linter set_option linter.declarationLimit.max 2 def a := 1 def b := 2 def c := 3

构建文件时会显示检查警告：

this file contains 3 declarations, more than 2

Note: This linter can be disabled with `set_option linter.declarationLimit false`

26.3.3. 有状态检查器🔗

与命令检查器一样，每条命令精译后都会调用有状态检查器。 它们同样可以访问命令的信息树与环境。 不同之处在于，它们并不独立于此前命令的检查结果。 相反，它们具有在整个模块中累积的状态。 因此可以检查非局部性质，并在违规发生后立即发出警告，而无需等待文件剩余部分处理完毕。

此外，有状态检查器分为“早期”和“晚期”两个阶段运行。 命令精译完成后，先运行所有有状态检查器的早期阶段，再运行所有晚期阶段。 这样就可以协作：早期阶段可以计算多个检查器的晚期阶段要使用的数据。 早期阶段是可选的，许多有用的有状态检查器并没有早期阶段。 通过注册检查器返回的句柄，有状态检查器不仅可以读取自己的已保存状态，也可以读取其他任何有状态检查器的状态。

有状态检查器通过 Lean.Elab.Command.registerStatefulLinter 注册。 与其他检查器注册函数一样，必须在元阶段的 Lean.Parser.Command.initialize : commandinitialize 块中调用。 检查器必须公开。 注册函数以早期和晚期阶段的实现为实参。 与其他检查器注册操作不同，该注册会返回一个有用的值，即可用于读取检查器状态的句柄。 StatefulLinter 和 registerStatefulLinter 都接受两个类型参数：第一个是在命令间传递的状态，第二个是早期阶段计算的数据。

有状态检查器也会在模块末尾运行。 由于它们已能从各命令中收集信息，因此可以提供模块检查器无法提供的反馈。

注册一个有状态检查器，并返回它的句柄（其他检查器可用该句柄读取它的状态）。 必须在初始化期间调用。

生命周期阶段

  • pre：通过 readPrevPostState 读取上一条命令的持久状态，并可输出一个前置阶段状态（类型为 Option τ）。

  • post：通过 readPrevPostState 和 readCurrentPreState 读取上一条命令的状态与当前所有前置阶段的输出，然后为下一条命令生成新的状态（类型为 σ）。

状态访问规则

  • 自身：通过 selfPrevPostState 和 selfCurrentPreState 直接访问自己的持久状态和前置阶段状态。

  • 其他检查器：只能通过 readPrevPostState 和 readCurrentPreState 闭包访问；这些闭包接受其他检查器的带类型句柄。

含解析错误的命令

与普通检查器不同，有状态检查器也会在含解析错误的命令上运行。 其消息会被丢弃（除非设置了 showPartialSyntaxErrors），但信息树会保留，因此 MessageData.hint 提供的代码操作仍会出现，却没有对应的消息。 当 (← read).suppressElabErrors 为真时，检查器不应生成提示。

落实文件布局

此有状态检查器检查模块是否具有指定结构。 模块应先有模块文档字符串，再设置所需选项，最后包含声明。 检查器的状态是跟踪此顺序的简单状态机。 每当遇到命令，它就局部检查不变量并更新状态。

26.3.4. 环境检查器🔗

项目构建完成后，若启用了 --builtin-lint，或在 Lake 配置中启用了 builtinLint 字段，lake lint 就会运行环境检查器。 Lake 构建项目后，其内置检查器会遍历各库目标的根模块，导入模块，再对所得环境运行所配置的环境检查器。 每个环境检查器由测试过程及成功、失败消息组成。 与命令和模块检查器不同，环境检查器不需要被待检查模块传递导入。

与其他检查器一样，环境检查器由选项控制。 与检查器本身不同，选项声明必须被传递导入。 控制环境检查器的选项会被特别注册，并在精译期间保存其值；因此检查器能从导入环境中取得这些值，包括使用 Lean.Parser.Command.in : commandin 局部设置的值。

定义环境检查器的步骤如下：

  1. 在一个模块中，于元阶段注册控制该检查器的公开选项。 在 Lean.Parser.Command.initialize : commandinitialize 块中运行 addEnvLinterOption，指示 Lean 在精译期间跟踪该选项值。 每个需要使用此检查器的模块都应传递导入该模块。 初始化块必须在元阶段运行。

  2. 在第二个模块中定义检查器本身。 使用 Lean.Linter.EnvLinter.builtin_env_linter : attr定义用于注册环境检查器的 `builtin_env_linter` 属性。 每个环境检查器都需要一个已注册的布尔值 `Lean.Option`，通过在属性中提供选项名与其关联，例如 `@[builtin_env_linter linter.envLinter.myLinter]`。builtin_env_linter 属性将检查器与选项关联。 待检查模块无需导入该模块，但被检查目标的根模块必须传递导入它。

26.3.5. 记录代码质量条目🔗

每个保存的值称为一个 Entry。 通过 Lean.Linter.logCodeQualityEntry 保存它们。 类似于 logLintIf，logCodeQualityEntryIf 接受检查器选项名，在对应检查器启用时记录条目，并考虑检查器集合、linter.all 和 --lint-only 选项。

代码质量条目关联度量名称、来源和值。 度量名称可以是任意字符串，但为避免冲突，通常应以检查器选项名作为前缀。 仅使用检查器名称可能与 Lake 自动输出为代码质量度量的检查警告计数冲突。 辅助函数 Lean.Linter.findCodeQualitySource 和 Lean.Linter.findCodeQualitySource? 从文件解析出的语法确定 Source；前者找不到声明时会回退为当前模块。 来源只能是模块或声明，无法将条目归属于更小的单位。 不过，可以使用字典值编码更细的结构。 值可以是浮点值，或从字符串到浮点数的字典。 计数等整数度量也应使用浮点数。

对给定来源，同一度量名称可以记录任意多次。 使用方负责适当地汇总度量。

检查器首先使用 simpLemmaStarts 遍历命令语法，找出每个显式 simp 引理的源码位置。 由于 simp 引理列表允许将引理应用于实参，因此使用开始位置来标识引理。 随后 simpUsage 检查器本身利用信息树，找到从这些位置开始的常量引用，记录一个字典度量，将完全解析后的名称映射为出现次数。

module public meta import Lean.Linter.Basic public meta import Lean.Linter.Util open Lean Elab Command Linter open Std (HashSet) meta section public register_option linter.simpUsage : Bool := { defValue := true descr := "record which lemmas are passed to `simp` as code quality \ metrics" } partial def simpLemmaStarts (stx : Syntax) : Array String.Pos.Raw := Id.run do let mut starts := #[] if stx.isOfKind ``Parser.Tactic.simpLemma then -- The lemma itself follows the optional `↓`/`↑` and `←` modifiers. if let some pos := stx[2].getPos? then starts := starts.push pos for arg in stx.getArgs do starts := starts ++ simpLemmaStarts arg return starts def simpUsage : Linter where run := withSetOptionIn fun stx => do unless getLinterValue linter.simpUsage (← getLinterOptions) do return let starts := simpLemmaStarts stx if starts.isEmpty then return -- Each lemma occurrence is identified by its position, since the -- info tree can contain several nodes for the same syntax. let mut found : HashSet (String.Pos.Raw × Name) := {} for tree in (← getInfoState).trees do found := tree.foldInfo (init := found) fun _ info found => match info with | .ofTermInfo ti => match ti.expr.constName?, ti.stx.getRange? with | some n, some r => if starts.contains r.start then found.insert (r.start, n) else found | _, _ => found | _ => found let mut counts : Std.TreeMap String Float := {} for (_, n) in found do counts := counts.alter n.toString fun c => some (c.getD 0.0 + 1) unless counts.isEmpty do Linter.logCodeQualityEntryIf linter.simpUsage { name := "linter.simpUsage.lemmas" source := ← Linter.findCodeQualitySource stx value := .dict counts } initialize addLinter simpUsage

26.3.6. 包级代码质量检查🔗

包级代码质量检查可以度量整个库或可执行目标的性质，而不是孤立地度量单个声明或模块。 它们在 Lake 配置文件或命令行中配置，不需要被待度量的代码导入。 包级检查输出代码质量条目。 由于作为 Lean 和 Lake 的一部分运行，它们可以访问 Lean 的元编程功能，无需各自构建特设机制。 用于落实包级限制或不变量的脚本只需解析 JSON，而不必以复杂方式与 Lean 代码交互。

将定义检查的模块加入 Lake 配置中的 checks 字段，或使用 Lake 的 --checks 选项，即可启用包级检查。 在所配置的检查模块中，每个检查都是 meta 阶段中类型为 PackageCheck 的公开定义，并使用 package_code_quality_check 属性注册。 给定 PackageCheckContext 类型的实参，包级检查可以使用 MetaM 的任意功能计算代码质量条目数组。 上下文指定库或可执行文件的根模块以及工作区的源码搜索路径。 包级检查不应通过抛出异常来表示包违反不变量或预期性质；应将问题作为条目返回，由数据使用方检查。

只有传入 --code-quality 或 --checks 选项时，才会运行启用的检查；否则 lake lint 不运行它们。 对于每个根模块，全部注册的包级检查会并发运行，结果条目追加到总体质量度量集合中。 通过库的模块匹配模式字段纳入的模块不被视为根。 即使自定义目标会构建 Lean 代码，也不会纳入检查；非默认的库和可执行目标同样不会纳入。 若在命令行指定模块，则检查这些模块，代替默认目标的根模块。 包级检查抛出的异常会写入标准错误，但不会终止代码检查。 若抛出过任何异常，lake lint 返回非零退出码。

检查在已导入根模块的环境中运行。 被多个根模块导入的模块可能被包级检查重复检查。 若根模块使用模块系统，即是一个模块，该环境仅包含公开和服务器信息，私有声明不可见。 若根模块不使用模块系统，私有信息也可见。 每个根模块都在新的环境中检查。

寻找重复定理

由于包级检查可以访问整个库，因此可用于寻找重复定理。 本示例检查有局限：它只找到几乎完全相同的定理，不考虑假设重排或定义展开。 更实际的检查可以使用更细致的相似性度量，报告超过某个相似阈值的定理。

首先将 Checks 模块加入包的 checks 字段：

name = "dups"
defaultTargets = ["Code"]
checks = ["Checks"]

[[lean_lib]]
name = "Checks"

[[lean_lib]]
name = "Code"

其唯一检查首先计算定理的等价类。 通过检查类型是否为命题来识别定理，并跳过作为其他声明辅助项生成的内部定理。 使用哈希表将非内部定理分成等价类；Lean.Expr 的 BEq 实例及对应的 Hashable Lean.Expr 实例在忽略绑定变量重命名和绑定信息变化的意义下检查相等性。 仅搜索根模块所在包中的模块。 因此，仅假设名称或隐式参数状态不同的定理会被归为一组，假设顺序不同的定理则不会。 确定等价类后，对包含多个元素的每个等价类中的每个元素，添加一个列出整个等价类的度量条目。

module public meta import Lean.Linter.CodeQuality.Frontend public meta import Lean.Compiler.ModPkgExt open Lean Meta Linter CodeQuality meta section @[package_code_quality_check] public def duplicateTheorems : PackageCheck where run ctx := do let env ← getEnv let some rootIdx := env.getModuleIdx? ctx.topLevelModule | return #[] let pkg := env.getModulePackageByIdx? rootIdx -- Group the theorems of the package's modules by their statements. -- Each equivalence class is a dictionary that maps its members' -- names to 1.0 to facilitate reporting. let mut classes : ExprMap (Std.TreeMap String Float) := {} let mut theorems := #[] for h : i in 0 ... env.header.moduleData.size do unless env.getModulePackageByIdx? i == pkg do continue for declName in env.header.moduleData[i].constNames do if declName.isInternalDetail then continue let some info := env.find? declName | continue unless ← isProp info.type do continue classes := classes.alter info.type fun dups? => some ((dups?.getD {}).insert declName.toString 1.0) let modName := env.header.moduleNames[i]! theorems := theorems.push (modName, declName, info.type) -- Report each theorem that has duplicates. let mut entries := #[] for (modName, declName, type) in theorems do let some dups := classes[type]? | continue if dups.size < 2 then continue entries := entries.push { name := "duplicateTheorems" source := .declaration modName declName value := .dict dups } return entries

代码本身包含同一定理的多个重述，其中三个属于同一等价类。 zero_add' 和 add_zero_rev 的陈述则不同。

module public theorem add_zero' (n : Nat) : n + 0 = n := rfl public theorem zero_add' (n : Nat) : 0 + n = n := Nat.zero_add n module public import Code.Basic public theorem add_zero'' (m : Nat) : m + 0 = m := rfl public theorem also_add_zero (k : Nat) : k + 0 = k := add_zero' k public theorem add_zero_rev (n : Nat) : n = n + 0 := rfl module public import Code.Basic public import Code.Extra
